# Мульти-столы и data-driven чернильница

Дата: итерация 0. Файл фиксирует решения, которые влияют на схему данных и GUI.

## 1. Типов столов может быть больше одного

Тип стола — это **датапак-определение**, а не Java-класс:

```
data/<namespace>/libresearch/table_type/<id>.json
```

Один тип задаёт:

- `display` — имя (пока литерал, в итерации 6 переедет на lang-ключи);
- `disciplines[]` — свои дисциплины: `id`, `display`, `color`, `icon`, `payout`,
  `count_per_point`;
- `bonus_blocks[]` — свои бонусные блоки: `block`, `display`, `cards[]`, `cost`.

Блок стола лишь ссылается на id типа по умолчанию. BlockEntity хранит `table_type`
в NBT, поэтому тип переживает перезаход и может быть сменён без замены блока
(пригодится для KubeJS и для «апгрейда» стола).

Сейчас в игре два типа и два блока:

| Блок | Тип | Дисциплины | Бонусные блоки |
|---|---|---|---|
| `libresearch:research_table` | `libresearch:research` | медь, железо, золото, алмаз, незерит, звезда Незера | верстак, печь, плавильня, стол кузнеца, стол зачарований |
| `libresearch:debug_table` | `libresearch:debug` | красный, оранжевый, жёлтый, лаймовый, синий краситель | камень, обсидиан, бедрок |

Отладочный стол нужен, чтобы проверять:

- независимые наборы дисциплин и наград;
- подсветку бонусных блоков на дешёвых/наглядных блоках;
- что тип стола действительно берётся из данных, а не из кода.

### Как добавить третий стол

1. Положить `table_type/my_table.json`.
2. Зарегистрировать блок (Java или KubeJS), который ссылается на этот тип.
3. Ничего в логике ядра менять не нужно.

Ограничение текущего скелета: блок задаёт тип жёстко в конструкторе
(`ResearchTableBlock(properties, tableTypeId)`). Когда появится KubeJS-регистрация,
нужен один generic-блок + способ передать тип: blockstate-свойство, компонент
предмета или NBT при установке. Решение примем в итерации 7, до этого плодить
классы дешевле, чем тащить блокстейт.

## 2. Подсветка бонусных блоков в GUI

Требование заказчика (итерации 3–4):

- показываются **все** бонусные блоки из `bonus_blocks`, даже если блока рядом нет;
- **недостающий** блок — тусклый;
- **присутствующий** рядом — обычный;
- **выбранный** игроком — подсвеченный;
- при наведении — тултип: что это за блок (и, позже, какие карты он даёт).

Состояния вычисляются так:

| Состояние | Условие |
|---|---|
| missing | блок не найден в области сканирования |
| present | найден, но не выбран |
| selected | найден и выбран (стоит −1 вдохновения) |

Сканирование (итерация 4): область 9×9×3 (по горизонтали ±4, по вертикали ±1)
плюс сущности в кубе ±5; один тип учитывается один раз; обновление раз в 100 тиков.

Данные для этого уже есть: `TableType.BonusBlock`. В итерации 0 GUI нет, поэтому
состояния пока только в модели.

## 3. Чернильница — тоже data-driven

```
data/<namespace>/libresearch/inkwell/<id>.json
```

Поля:

| Поле | По умолчанию | Смысл |
|---|---|---|
| `item` | — | предмет, к которому относится определение |
| `capacity` | 100 | полный заряд |
| `color` | `#1E1B18` | цвет жидкости (тинт предмета) |
| `charges_per_draw` | 1 | расход за розыгрыш карты |

Текущий заряд хранится в компоненте `libresearch:inkwell` (`charges`, `capacity`),
поэтому синхронизируется клиенту и переживает перезаход. Ёмкость из JSON
применяется при крафте/перезарядке (итерация 5); у стартового предмета она 100.

Ограничение: на выделенном сервере клиент не получает датапак-определения, поэтому
тинт может откатиться к дефолтному цвету. Для MVP это косметика; если станет важно —
дублировать цвет в компонент.
